# SANKETRA: Robustness-aware traffic-sign perception (technical report)
Every number below was produced by this project's scripts on a single laptop with an RTX 3050 Laptop GPU (4 GB); nothing is quoted from the literature: Section 2 cites papers for context only, and no published results are compared with the numbers here (different splits, class groups and test sets make such comparisons invalid).

## 1. Introduction
Driver-assistance perception must find road signs reliably and know when it is unsure. This project builds an end-to-end prototype (live video, detection, tracking, event log, interface) and studies how its quality changes under difficult image conditions. Contribution: a measured robustness and calibration study of a small detector, an uncertainty-aware interface (an abstention flag; temperature calibration is implemented and evaluated offline but off by default in the live app), and an honest evaluation methodology. No claim of novelty over the literature is made; Section 2 places the work in context.

## 2. Related work
**Traffic-sign benchmarks.** Houben et al. introduced the German Traffic Sign Detection Benchmark (GTSDB) with a fixed evaluation protocol, deliberately separating detection from classification and scoring performance on categories of signs (prohibitory, danger, mandatory) rather than on every class [1]. SANKETRA uses this benchmark and its category idea, plus an additional "other" group. Tsinghua-Tencent 100K (TT100K) was built from 100,000 Tencent Street View panoramas, contains about 30,000 sign instances with class labels, boxes and pixel masks, and covers varied lighting and weather [2]; its signs are Chinese and the project page states a non-commercial (CC BY-NC) licence. The Mapillary Traffic Sign Dataset (MTSD) offers about 105,000 street-level images from around the world with roughly 400 annotated sign classes, free for academic research [3]. Whether MTSD contains usable Indian sign images was not checked in this project and would have to be verified before relying on it. Large public benchmarks therefore exist for German, Chinese and global signs, but no ready-to-use Indian road-scene sign dataset was obtained or evaluated in this project. The Kaggle "Indian Traffic Sign Dataset" that this project did examine contains 32x32 cropped classification images and is not a detection dataset (see docs/INDIAN_SIGNS_PLAN.md). The INDRA dataset [8] provides 104 Indian road videos recorded from a head-mounted camera, but it is annotated for safe road-crossing durations, not for signs.

**Detection and tracking.** YOLO-style detectors predict boxes and class scores from an image in a single network pass, which suits real-time use [4]; this project fine-tunes small YOLO11 models from the Ultralytics library; its documentation says no academic paper has been published for YOLO11, so it is cited as software [9]. For video, ByteTrack links detections over time and, unlike methods that discard low-score boxes, also matches low-score detections to existing tracklets, which helps with occlusion and fragmented trajectories [5]. SANKETRA uses it to give each sign an identity so that events and smoothing operate per object.

**Calibration.** Guo et al. showed that modern neural networks are often poorly calibrated and that temperature scaling, a single-parameter variant of Platt scaling, is a simple and effective post-hoc fix, with expected calibration error (ECE) as a summary measure [6]. That work studies classification; SANKETRA applies the same idea to a detector's box confidence, which is an adaptation and not something [6] evaluates. Temperatures fitted here on German validation data are not assumed to transfer to other domains.

**Robustness to corruptions.** Hendrycks and Dietterich built ImageNet-C to measure how classifiers degrade under common corruptions at graded severities [7]. This project follows that idea at a much smaller scale: five simulated corruptions (brightness, blur, noise, low resolution, low light) at six severity levels, applied to a detector's test set. These are not the ImageNet-C corruptions and the severities are not comparable with theirs.

**Gap addressed (modest).** Published sign-detection work mostly reports accuracy on benchmark test sets. This project adds an end-to-end, honest demonstration: measured per-condition degradation and calibration for a small detector, an interface that shows uncertainty and abstains, and explicit records of what was not measured. It makes no claim to beat any published result.

## 3. System design
Pipeline: capture (OpenCV) -> YOLO11n detector (+ optional general object model) -> ByteTrack -> optional temperature calibration (default 1.0 = off) -> per-track smoothing -> abstention flag -> sign registry -> overlay and event log -> binary WebSocket -> React console. FastAPI backend, React/TypeScript frontend, persistent data folder. Design decisions with evidence: FP32 instead of FP16 (measured earlier: FP16 cost about 3 s on every new input shape and gave no speed gain, docs/PERFORMANCE.md; recent app logs show a 1.5 to 4 s first call per new frame size in FP32 as well, counted as warm-up, so re-check this comparison before presenting it as a major finding); frames are processed one at a time so latency cannot accumulate; binary frames and canvas painting keep the UI responsive.

## 4. Data
GTSDB (FullIJCNN2013): 900 images, 1,213 boxes in 43 sign classes grouped into 4 challenge categories (mapping file configs/gtsdb_categories.json, first written from memory, then verified against the category printed next to each class in the dataset's ReadMe.txt using `python -m training.adapters.check_gtsdb_categories`. Result on 1 Nov 2026: all 43 classes match the ReadMe categories). Counted in the downloaded files on 1 Nov 2026: 900 .ppm images and 1,213 lines in gt.txt (one line per box); a third-party summary lists 1,206 signs, so the exact figure used here is the project's own count. Split by blocks of 10 consecutive images to limit leakage between near-identical frames: 631/149/120 images. Test instances: prohibitory 80, other 40, mandatory 21, danger 20. Limitations: German signs only; 4 groups; small test set.

## 5. Method
YOLO11n fine-tuned for 30 epochs (seed 0), and for 100 epochs with training seeds 0, 1 and 2, plus YOLO11s for 100 epochs (seed 0), for the controlled comparison (batch 8, 640 px, no horizontal flips; the data split is fixed). Evaluation: precision, recall, mAP@0.5, mAP@0.5:0.95 per class on the held-out test split; latency; robustness with five seeded simulated corruptions at six severities; calibration with temperature scaling fitted on validation and reported on test (reliability diagram, ECE); temporal smoothing measured as flicker rate on unlabelled road clips (stability only, see section 6).

## 6. Results (measured)
See docs/MODEL_CARD.md for tables. Findings:
1. Detection quality on clean test data (yolo11n, 30 epochs, seed 0): mAP@0.5 0.929, mAP@0.5:0.95 0.739. Weakest group: mandatory (recall 0.714, 21 test boxes).
2. Speed: model-only median latency was 13.6 to 27.5 ms per image on the GPU at 640 px across runs of the same yolo11n architecture on different days (15 to 16 ms in the first run). The full Console pipeline (second model, tracker, drawing, WebSocket) was only read by eye from screen recordings: about 7 to 14 FPS in the best recordings and slower when the GPU was shared, so the live demo is described as "several frames per second", not as real-time.
3. Robustness (yolo11n, 30 epochs): low light is the hardest condition (mAP@0.5 0.929 -> 0.447 at severity 5), then noise (0.578) and low resolution (0.683); brightness (0.838) and blur (0.806) are gentler. Precision stays above 0.76 while recall drops, i.e. failures are mostly silent misses.
4. Calibration (yolo11n, 30 epochs): fitted temperature 0.52 (< 1) means raw scores were under-confident; ECE improved from 0.122 to 0.070. The test set is small, so this is indicative.
5. Model-size comparison (controlled: same data, split, seed and 100 epochs): yolo11s reaches test mAP@0.5 0.970 / mAP@0.5:0.95 0.847 (19.2 MB); yolo11n reaches 0.929 / 0.767 with seed 0 and 0.935 / 0.767 averaged over three training seeds (5.5 MB). The earlier yolo11n run with 30 epochs scored 0.929 / 0.739, so extra epochs changed only box tightness (mAP@0.5:0.95 +0.028), while model size accounts for most of the remaining gap (about +0.04 mAP@0.5 and +0.08 mAP@0.5:0.95; +0.035 and +0.080 against the three-seed yolo11n mean). Model-only latency of the same yolo11n architecture ranged from 13.6 to 27.5 ms (median at 640 px) across runs on different days, which overlaps yolo11s's 19.0 ms, so no speed difference between the two sizes is claimed. At the harshest corruptions all three runs fall to the same mAP@0.5 (yolo11n 100 epochs / yolo11n 30 epochs / yolo11s; low light 0.446 / 0.447 / 0.448; noise 0.575 / 0.578 / 0.575), so capacity alone does not buy robustness there. yolo11n was trained with three training seeds (same split): mean test mAP@0.5 0.935 (range 0.929 to 0.942, sd 0.006, 95% t-interval 0.919 to 0.951) and mean mAP@0.5:0.95 0.767 (range 0.765 to 0.767, interval 0.764 to 0.769); yolo11s was trained once, and its 0.970 / 0.847 lies outside those intervals. The intervals cover training randomness only, not test-set sampling error (120 images, 160 boxes), and seed 0 used Ultralytics 8.4.194 while seeds 1 and 2 used 8.4.197.
6. Temporal consistency (stability only, no ground truth): on four unlabelled Indian road clips, EMA smoothing of tracked-object confidence (generic COCO detector, 290 tracks) lowered the flicker rate from 0.128 to 0.067 pooled, a 46 to 60 percent reduction in every clip; holding a box for 3 missed frames added at most a few points (0.064 pooled). The sign model produced only 14 tracks on the longest clip (flicker 0.234 -> 0.120 with EMA, 0.098 with hold 3), too few to conclude anything about signs. Limits: stability is not accuracy (a steady false detection scores well), delay and missed-detection cost were not measured, tracks within a clip are not independent, one run with default settings.

## 7. Interface and engineering
Live console (video or webcam, several frames per second on the target laptop; see the latency note in the model card), confidence score with UNCERTAIN flag (temperature calibration optional, off by default), tracking IDs, event timeline with frame inspection and CSV/JSON export, Perception Lab with simulated conditions, Results page that only shows measured files, sign registry. 40 automated tests (API, WebSocket streaming, data pipeline, calibration, corruptions). Performance work was driven by measurement (docs/PERFORMANCE.md), including reverting two changes that measurements showed to be harmful.

## 8. Limitations and ethics
Prototype, not a certified automotive system. German data only; no Indian sign recognition yet. Small test set (160 boxes); yolo11n has three training seeds with intervals, yolo11s one run, and no interval covers test-set sampling error. Live timing is noisy and was read by eye. Test videos: the INDRA clips (licence listed as unknown), a Kanpur highway clip and video01 (sources not recorded) were used privately for informal tests and are not redistributed. Simulated corruptions. Group-level classes. High confidence is not correctness; the abstention threshold is a user setting, not a safety guarantee. Registry: 9 of 10 Indian sign entries were checked against the Delhi Traffic Police public sign guide (not against IRC:67 or the legal drawings), one entry and the German group entries remain unverified, and Hindi labels are empty.

## 9. Future work
Indian-sign training and evaluation (own labelled footage or a licensed public Indian dataset; docs/INDIAN_SIGNS_PLAN.md; the Kaggle 32x32 set was checked and rejected), a labelled temporal study that also measures smoothing delay, per-sign classes, real night/rain footage, more seeds for yolo11s and a bootstrap over test images, a two-stage classifier for sign identity.

## 10. Conclusion
SANKETRA is a working end-to-end prototype for traffic-sign perception on a laptop GPU: live video or webcam input, detection, tracking, a confidence score with an uncertainty flag (temperature calibration is available but off by default), an event log, and a console with a robustness lab and a results page that shows only measured files. On the German GTSDB benchmark, grouped into four categories, a yolo11n model reached test mAP@0.5 0.935 (mean of three training seeds, 95% interval 0.919 to 0.951) and a yolo11s model 0.970 (one run; 120 test images, 160 boxes, so test-set sampling error is not covered). In a controlled comparison (same data, split, seed and 100 epochs) most of the gap between the two models was due to model size, while extra epochs for yolo11n mainly tightened boxes (mAP@0.5:0.95 0.739 to 0.767). Simulated corruptions showed that precision stays high while recall falls, so failures are silent misses; low light and noise were the hardest, and all three trained models reached about the same accuracy at the most severe settings. Temperature scaling reduced ECE to about 0.04 to 0.07 on German test data, but the live app applies no calibration by default. A temporal study on four unlabelled Indian road clips showed that EMA smoothing roughly halved display flicker of tracked objects (0.128 to 0.067 over 290 tracks from a generic detector); the sign model produced too few tracks to conclude anything, and stability is not accuracy.
What was not achieved: no Indian-sign recognition. The German-trained model produced false alarms on Indian street scenes (for example a shop logo labelled as a sign), and the only Indian sign dataset checked in detail was unsuitable for detection. Registry meanings are only partly verified (9 of 10 Indian entries against one public guide; no Hindi labels). The results describe German signs in four groups on a small test set and must not be read as evidence of accuracy on Indian roads or of real-world safety. The most valuable next step is a labelled Indian dataset built from own footage, with a reviewed test set, multiple seeds and confidence intervals.
